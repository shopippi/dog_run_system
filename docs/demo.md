# ブラウザだけで動くデモ(apps/demo)

Cloudflare のアカウントがなくても、ブラウザだけでこのシステムを本物の動きで触れるデモ。
静的なファイル(HTML・JS)だけで動き、クラウドの API は呼ばない。
お客さん向け画面(apps/liff)と受付・管理画面(apps/admin)は本物の画面をそのまま使い、
API(apps/api の Hono)とデータベースの処理(SQLite)もブラウザの中で動かしている。

`docs/demo.html` は打ち合わせ用に手で作った画面の模型。こちらは実装したシステムそのものが動く。

## 開き方

```sh
pnpm install
pnpm --filter @dr/demo build              # apps/demo/dist/ にできる
npx http-server apps/demo/dist -p 8796    # http://localhost:8796/ を開く
```

- `apps/demo/dist/` の中身を、そのまま静的なファイルの配信先(Cloudflare Pages、GitHub Pages など)に置いても動く。パスはすべて相対パス。
- https か localhost で開く(パスワードの処理にブラウザの暗号の機能を使うため、http の別のアドレスでは動かない)。
- SQLite の本体(WASM、約650KB)はビルドに同梱している(`dist/sql-wasm.wasm`)。読めないときだけ cdnjs、jsDelivr の順に読む。
- 新しめの Chrome・Safari・Edge・Firefox で動く。

## 画面の構成

- 上: 打ち合わせ用の手順(9つの場面)。押すと、その場面に必要な状態まで進める。
- その下: デモの「今日」の日付と、「翌日にする」「夜間の処理を今すぐ動かす」「最初からやり直す」。
- 左: お客さんのスマホ(LINE の中で開く画面)。上で LINE のアカウントを切り替えられる。
  - 「LINE のトーク画面」: LINE 公式アカウントのトーク画面と、下のリッチメニュー(`docs/line/richmenu.md`)を再現する。メニューを押すと、その画面が LINE の中で開いたように出る(上の帯の × でトークに戻る)。
  - 「受付の QR を読み取る」: 受付の QR コードを読み取ったときと同じ画面(チェックイン)を開く。
  - 「リッチメニューから開く」: 会員証を開く。
  - 「LINE のトーク」: 家族の招待を送ると、ここに届く。「この招待を開く」で、いま選んでいるアカウントで開く。
- 右: 受付・管理画面。「ログインする人」で受付スタッフ・管理者・製作者を切り替える。

## 手順(打ち合わせ用)

| | 場面 | 使うもの |
| --- | --- | --- |
| 1 | はじめてのお客さん | 「はじめての人」のアカウント。写真は手元の画像を選べる |
| 2 | 9ポイントのおうちがチェックイン | こむぎママ(DR-000001、9ポイント)。10ポイントになると会員証の「無料券と交換する」で無料券に交換し、右へスライドして「使用できました」の画面を出す(今日の来場に印が付く) |
| 3 | ママがパパを招待 | こむぎママの「家族を招待」→ LINE のトーク → こむぎパパに切り替えて「この招待を開く」 |
| 4 | パパも同じ日にチェックイン | こむぎパパ。ママが今日チェックイン済みなので、ポイントは増えず「だいず」の追加だけ(先に手順2と3) |
| 5 | 別々のおうちを、招待からまとめる | taka_papa(DR-000002)から届いた招待を nico.mama(DR-000003)が開き、その場でまとめる。管理画面は操作ログ(お客さんの操作として残る) |
| 6 | 名前・写真・ポイントを管理者が変更 | こむぎ・だいずのおうちの詳細(呼び名・犬の名前・写真・ポイント)。操作ログから元に戻せる |
| 7 | 旧カードの引き継ぎ(受付で直接入力) | ももママ(DR-000004)が受付で紙のスタンプカードを見せた場面。管理画面の「旧カードの引き継ぎ」で、カードの種類とポイント数を入れ、「旧カードを目で確かめた」「紙のカードは回収した」に印を付けて引き継ぐ |
| 8 | 受付・製作者の権限 | 受付スタッフでログインし直す(管理者だけの画面はメニューに出ない)。製作者はすべて見られるが変更できない |
| 9 | 預かり・お泊まりの予約 | こむぎママの「預かり・お泊まりの予約」。だいず(はじめて)を予約すると確認待ち → 右の「確認待ちの予約」で承認 → お客さんの画面が確定になり、「LINE のトーク画面」に確定のお知らせ(デモでは送ったつもり)が出る。こむぎだけならすぐ確定。6日後は中型が満員、9日後は休み |

どの場面も、本物の管理画面(おうちの統合・旧カードの引き継ぎ・おうちの詳細・操作ログなど)がそのまま動く。

## 初期データ

- おうち 30 件(犬 1〜3 頭、家族が2人のおうち 5 件)。うち DR-000001〜DR-000004 は手順で使う固定のおうち。
- 来場 半年分(およそ 600 件。土日に多く、雨の日は少なく、イベントの日は多い)と、会員以外の来場。
- ポイントと無料券は台帳どおり(来場ごとに +1。10 ポイントたまったら会員証で無料券と交換した扱い。使った券もある)。
- 天気 半年分、2026 年の祝日、イベント 4 件、休業日 2 件。taka_papa から nico.mama への、まだ開いていない家族の招待 1 件。旧カードの移行期間(前後1か月)。確認待ち(以前の申請)はない。
- 預かり・お泊まりの予約 およそ1か月分(今日の前後。利用済み・確定・確認待ち・キャンセル・来なかった。受け入れ数を超えない)。こむぎは預かったことがあり、だいずははじめて。6日後は中型の預かりが満員、9日後は預かりが休み(研修)。一部のワンちゃんは「預かり経験あり」の印つき。
- 自動処理の実行の履歴(直近の数日分の成功)。「システムの状態」の画面は、はじめから青(正常)で出る。
- 犬の写真は、最初の 10 おうち分だけ、簡単な犬の絵を使う。
- 会員証の背景は、DR-000001 が写真(犬の絵)、DR-000002 が紺、ほかは初期値(墨)。

乱数は固定の種から作るので、やり直すたびに同じデータになる(日付だけは、その日の「今日」に合わせて動く)。

## できること

- お客さんの登録(写真つき)、チェックイン、会員証(背景の変更・肉球のスタンプ)、無料券の交換と使用、犬の追加・変更・登録のおやすみ、プロフィール、家族の招待と参加、招待からおうちをまとめる。
- 受付の今日の来場、取り消し、代理チェックイン、会員以外の頭数、おうちを探す。
- 預かり・お泊まりの予約(お客さんの予約・一覧・キャンセル、管理画面の予約カレンダー・確認待ち・手入力・状態の変更・予約の設定)。予約が確定・お断りになると、「LINE のトーク画面」に届くはずのメッセージが出る(デモでは LINE に送らない)。
- 管理者の画面: ダッシュボード、おうちの詳細(呼び名・犬の情報と写真・ポイントと無料券の手動登録・無料券を使用済みにする・家族)、おうちの統合と元に戻す、旧カードの引き継ぎ(直接入力と一覧)、イベントと休業日、アンケートの質問、犬種、ルールの設定、スタッフ、CSV出力、操作ログと元に戻す、使い方・困ったとき、システムの状態。
- 製作者(見るだけ)でのログインと、受付スタッフの権限の違い。
- 「翌日にする」で日付を進め、翌日のチェックインや、10ポイントたまって無料券と交換する流れを見せられる。
- データはブラウザの中(IndexedDB)に保存され、再読み込みしても続きから使える。「最初からやり直す」で初期データに戻る。

## できないこと・本物との違い

- 本物の LINE ではない。LINE のログイン・トークへの送信・カメラでの QR の読み取りは、デモの画面の中のまねで動く。
- 犬の写真は本物ではない(初期データは絵。自分で選んだ画像は使える)。
- データはこのブラウザの中だけにある。ほかの人やほかの端末とは共有されない。ブラウザのデータを消すと消える。
- 天気・祝日の取得など、外のサービスにつなぐ処理はしない。デモでは `OFFLINE=1` で API を動かし、天気・祝日の処理は「スキップしました(インターネットにつながらない環境のため)。」として成功の扱いにする(「今すぐ実行」や「夜間の処理」でも赤くならない)。そのほかの夜間の処理(日別の集計・有効期限・バックアップ)はブラウザの中で動く。
- 受付の「今日の来場」は、本物では30秒ごとに新しくなる。デモでは、お客さんがチェックインするとすぐに読み込み直す。

## しくみ(開発者向け)

- `apps/demo/src/engine/`: `createApp()`(apps/api)をブラウザで動かす。D1 の代わりは sql.js の上の `DemoD1`、R2 の代わりはメモリの `DemoR2`。マイグレーションは `apps/api/migrations/*.sql` を番号順に当てる。
- ブラウザの Request / Response は Cookie と Set-Cookie を捨てるので、API に渡す Request のヘッダーを差し替え、Response は Set-Cookie を保つ形にしている(`http-patch.ts`)。管理画面のクッキーは画面ごとの入れ物で保つ。
- 画面との橋渡し: apps/liff と apps/admin は、`VITE_DEMO=1` でビルドしたときだけ `fetch` を差し替え(`src/lib/demo-fetch.ts`)、`/api/` と `/admin/api/` への要求を親の画面に `postMessage` で送る。URL はハッシュ(`#/checkin`)になる。
- 写真: `<img src>` に API の URL を書くと、ブラウザが直接取りに行って読めない。写真の部品(管理画面の `DogFace` と `usePhotoSrc`、お客さん向けの `DogAvatar` と `useAuthedImage`)は、写真を `fetch` で読んで `blob:` の URL にしてから出す。
- 時刻: 要求に `x-debug-now` を付けて、デモの「今日」を API に伝える(`ENVIRONMENT=local` のときだけ効く)。
- テスト: `pnpm --filter @dr/demo test`(D1 の代わりと初期データ)、`npx playwright test --project=demo`(画面の通し操作。デモは `E2E_PORT + 500` 番で配信する)。
- マニュアルの写真(`docs/images/manual/`)は、この初期データを e2e のデータベースに入れてから撮る(`pnpm manual:shots`。`e2e/manual-shots.spec.ts`。時刻は今日の 11:30 にそろえる)。
